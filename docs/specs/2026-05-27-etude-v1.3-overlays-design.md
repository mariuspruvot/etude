# Étude v1.3 — Design Spec: Curated overlays (closing the promotion loop / coverage layer 3)

- **Date**: 2026-05-27
- **Status**: **Design only — NOT approved for implementation.** Gated on explicit go-ahead.
- **Builds on**: v1.1 (`2026-05-27-etude-v1.1-design.md`, §9b layers) and v1.2
  (`2026-05-27-etude-v1.2-design.md`). v1.2 should be merged first.
- **Why separate**: this is a new milestone with its own schema and lint surface; isolating it
  keeps the v1.2 implementation plan focused and lets this design evolve independently.

## 1. Summary

v1.1 defined a **three-layer coverage strategy** (spec §9b):

1. Curated language **core** (the spine) — `tracks/<lang>/curriculum.md`, closed + linted.
2. **On-demand generation** (the long tail) — frameworks/libraries/niches generated live via
   Context7, remembered per-learner in `progress/<track>/extensions.md`.
3. **Promotion** — a popular personal extension graduates to a **shared, curated overlay**.

v1.1 proved layers 1 and 2. **Layer 3 was deferred** — there is no shape for a curated
overlay, no lint for it, and no defined path from a personal extension to a shared overlay.
v1.3 designs exactly that: the **overlay schema**, the **lint extension**, and the
**`extensions.md` → overlay promotion path**, without touching the closed core schema or its
lint.

## 2. Goals & Non-Goals

### Goals
- Define a **new, distinct schema** for a curated overlay attached to a parent language track.
- Define a **separate validator** (or an overlay mode of the existing lint) for overlays.
- Define the **promotion path**: personal extension (`x01`, `personal:foo`) → shared overlay
  (`<x>:foo`, linted).
- Define how overlay concepts are **tracked** in `skills.md` (namespaced, parent-track-local).

### Non-Goals
- NOT changing `tracks/<lang>/curriculum.md` schema or its lint (the core stays closed/linted,
  invariant).
- NOT shipping any actual overlay content (FastAPI, React, …) — this is the mechanism only.
- NOT making overlay concepts transverse (frameworks do not claim cross-track transfer).
- NOT auto-promoting — promotion stays a human PR (personal → community), opt-in.

## 3. Key Decision: overlay shape

A curated overlay is a **child of a language track**, not a standalone track:

> `tracks/<lang>/overlays/<name>.md` — e.g. `tracks/python/overlays/fastapi.md`.

Rationale (vs a dedicated `tracks/<x>/` track): a framework is **not** a language. It builds
on the parent's core concepts (FastAPI needs Python's `async-await`, `type-system`), has no
transverse spine of its own, and should be reachable as "Python + FastAPI", not as a peer
language. Modeling it as a child overlay makes the dependency explicit and maps cleanly onto
the v1.2 `personal:` prefix → overlay namespace at promotion time. A genuinely standalone
subject (its own language/spine) would instead get a normal `tracks/<x>/curriculum.md` — that
path already exists and is **not** what the overlay mechanism is for.

## 4. The overlay schema (NEW — distinct from `curriculum.md`)

> This is a **new schema**. It does not relax, extend, or reuse the closed `curriculum.md`
> schema. The core curriculum lint is untouched.

```markdown
---
kind: overlay                      # discriminator — distinguishes from a curriculum.md
parent_track: python               # MUST match an existing tracks/<parent_track>/curriculum.md
name: fastapi                      # overlay slug; also the concept namespace prefix
display_name: FastAPI
target_version: "0.11x"
freshness_source: context7
maintainers: [community]

concepts:
  # Overlay concepts are namespaced with `<name>:` and are NEVER transverse.
  overlay: [fastapi:routing, fastapi:dependency-injection, fastapi:pydantic-models, fastapi:async-endpoints, fastapi:testing-client]
  # Concepts from the parent track this overlay builds on (referenced, not redefined):
  requires_parent: [async-await, type-system, testing]
---

# FastAPI — Overlay (on the Python core)

> Builds on the Python core. Reachable as "Python + FastAPI". Not a standalone track.

## Modules

### o01 — Routing & request handling
- id: o01
- concepts: [fastapi:routing]
- prerequisites: [parent:async-await]      # may reference parent concepts via `parent:`
- ecosystem:
    libs: [fastapi, uvicorn]
- resources:
    - <current docs URL>
- mastery:
    - defines typed path/query/body params; returns typed responses
- exercise_seeds:
    - "implement a typed CRUD router with path + query params, no any"

### o02 — Dependency injection
- id: o02
- concepts: [fastapi:dependency-injection]
- prerequisites: [o01]                      # may reference earlier overlay modules
- ...
```

### Schema rules
- `kind: overlay` is the discriminator; the validator dispatches on it.
- `parent_track` MUST resolve to an existing `tracks/<parent_track>/curriculum.md`.
- Overlay concept ids MUST be namespaced `<name>:<concept>` and MUST be declared under
  `concepts.overlay`.
- `concepts.requires_parent` lists parent-track concepts the overlay depends on; each MUST
  exist in the parent's declared concepts (transverse or language_specific).
- Module `prerequisites` may reference: other overlay module ids (`oNN`), or parent concepts
  via a `parent:<concept>` form (the `parent:` concept MUST be in `requires_parent`).
- Module ids use an `oNN` series (overlay), distinct from the core's `mNN` and the personal
  `xNN`.
- Overlay concepts are **never transverse** and are **track-local to the parent** — they never
  drive cross-track skipping.

## 5. The lint extension (NEW validator surface)

The existing `tools/lint_curriculum.py` stays the **closed-core** linter, unchanged. Overlays
are validated by either (a) a new `tools/lint_overlay.py`, or (b) an `--overlay` mode in the
existing tool that dispatches on `kind`. **Decision deferred to the v1.3 plan**; both keep the
core path byte-for-byte unchanged. The overlay validator checks:

1. Frontmatter has `kind: overlay`, `parent_track`, `name`, `concepts.overlay`.
2. `parent_track` resolves to an existing core curriculum file.
3. Every overlay concept is namespaced `<name>:…` and declared in `concepts.overlay`.
4. Every `requires_parent` concept exists in the parent's declared concepts.
5. Every module `concepts:` entry is a declared overlay concept.
6. Every module `prerequisites` entry resolves to an earlier `oNN` module **or** a
   `parent:<concept>` whose concept is in `requires_parent`.
7. No transverse claims, no redefinition of parent concepts.
8. The DAG of overlay module prerequisites is acyclic.

The overlay lint is **additive**: running it over a repo with no overlays is a no-op; the
core lint never sees overlay files.

## 6. The promotion path (`extensions.md` → overlay)

Personal → community, as a human PR (never automatic):

| Personal extension (v1.1) | Curated overlay (v1.3) |
|---|---|
| `progress/<track>/extensions.md`, gitignored | `tracks/<lang>/overlays/<name>.md`, committed |
| module ids `xNN` | module ids `oNN` |
| concepts `personal:foo` | concepts `<name>:foo` (namespace = overlay slug) |
| not linted | linted by the overlay validator |
| track-local, per-learner | track-local to parent, shared |

Mechanical promotion: rename the `personal:` prefix to the overlay's `<name>:` namespace, set
`oNN` ids, add the required `kind`/`parent_track`/`requires_parent` frontmatter, fill
`resources` with current docs, and open a PR. The tutor can scaffold the file from the
learner's `extensions.md`; a human reviews and merges.

## 7. Tracking overlay concepts in `skills.md`

- Overlay concepts appear with their `<name>:` prefix (e.g. `fastapi:routing`).
- They are **track-local to the parent track** — scoped under the parent, never transverse,
  never satisfying another track's skip logic (same discipline as `personal:` in v1.2, but
  shared + linted).
- This means `skills.md` may carry three concept kinds: curated-core (transverse or
  language_specific), `personal:` (per-learner, track-local), and `<overlay>:` (shared,
  parent-track-local). All three coexist without changing the core schema.

## 8. Components that would be touched (when implemented)

- **New**: `tracks/<lang>/overlays/` directory + the overlay schema; `tools/lint_overlay.py`
  (or `--overlay` mode) + its tests.
- **Edited skills** (overlay awareness, analogous to v1.1 `extensions.md` awareness):
  `assess`, `teach`, `exercise`, `status` would read `tracks/<lang>/overlays/*.md` when the
  parent track is active and treat overlay modules as first-class (after their parent
  prerequisites are met).
- **Edited**: `grade`/`assess` skip logic to keep `<overlay>:` concepts parent-track-local.
- **Docs**: `README.md` (coverage strategy: layer 3 now real), `progress/README.md` (how an
  `extensions.md` module is promoted to an overlay), a contributor note on the overlay schema.
- **Unchanged**: core `curriculum.md` schema + `lint_curriculum.py`; integrity hook.

## 9. Assumptions

- *A child-overlay shape fits frameworks better than a standalone track* — chosen because
  frameworks build on a core and have no transverse spine; revisit if a "framework" turns out
  to genuinely deserve peer-track status.
- *A separate overlay validator keeps the core lint provably unchanged* — the safest way to
  honor the "core stays closed/linted, untouched" invariant; the new-tool vs `--overlay`-mode
  choice is a v1.3-plan detail, both satisfy it.
- *`oNN`/`xNN`/`mNN` id namespaces avoid collisions across core, personal, and overlay* —
  chosen so a single `skills.md`/`log.md` can reference all three unambiguously.
- *Overlay concepts stay parent-track-local (no transfer)* — frameworks are language-specific;
  cross-framework transfer claims would be garbage, same reasoning as v1.1's `personal:` rule.

## 10. Open questions (for the v1.3 plan, not blocking this design)

- New `tools/lint_overlay.py` vs an `--overlay` mode of `lint_curriculum.py` — both keep the
  core path unchanged; pick in the plan based on code-sharing vs isolation.
- Whether overlays may declare prerequisites on **other overlays** (e.g. a React-Router
  overlay on a React overlay) or only on the parent core — propose: parent + own modules only
  in v1.3; cross-overlay deps deferred until a real case appears.
- How `status`/`assess` present overlays in the path (inline with core modules vs a separate
  "extensions & overlays" section) — a presentation detail for the plan.
